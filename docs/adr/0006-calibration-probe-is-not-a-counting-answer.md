# A calibration probe is not a counting answer

A **calibration probe** seeds the item's starting level and nothing else: it leaves `lastCountedOn` untouched, so every calibrated item still has its **counting answer** available on the calibration day. This reverses the original rule, under which each probe *was* the item's day-1 counting answer (mvp-spec §8 before #37). A probe is an assessment, not a demotion — it establishes where the child stands, and spending the item's one level-changing answer of the day on that establishment is not a price the child should pay. Under the old rule the cost was concentrated exactly where it hurt most: right after calibration practically every wrong-probed item was affected, so a correct answer in the very first round moved neither `level` nor `lastPromotedOn`, and the **progress map** — whose level-up hint is derived from `lastPromotedOn == today` — showed a uniformly reward-free first round. The old rule also produced an asymmetry with no defensible content: items left unprobed by a **mercy stop** kept `lastCountedOn = null` and were fully countable that same day, while probed-wrong items were not.

The field is dropped in **both** probe branches, not only the wrong one. On the correct branch it is inert anyway, because `satisfiedOn = today` removes the item from the day's open set — dropping it there too removes a meaningless special case rather than adding one. `lastCountedOn` keeps its exact meaning ("has today's counting answer happened?"), so the persistence schema is untouched and no migration exists: only a user who calibrated *today* sees a difference, and the state self-heals at midnight. The claim that a fully fluent child reaches the **day goal** at the end of the first run still holds, but it now rests on `satisfiedOn`, not on the probe being a counting answer. Deliberately out of scope, and unchanged: inside a normal round a wrong answer still consumes the day's counting slot, and the mandatory same-round retry can never level the item up — there the first answer is the assessment and the retry is practice. This ADR exists so the coupling is not quietly restored later "for consistency" ([#37](https://github.com/ewirch/mulplu/issues/37)).
